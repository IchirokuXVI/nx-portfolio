Credential flows, plan 0009. The two front door buttons 0008 left recorded, plus the guest banner's action and what a confirmation link opens.

Phone only, 390x844, Night only: no new colour role, so a Day artboard would restate 0003 rather than find anything.

These are full routes, not sheets. 0008's rule is that a sheet completes one field in place; each of these is a destination with its own alternatives underneath.

REGISTERING SIGNS YOU IN IMMEDIATELY. identity.service register() issues tokens at the end and sends the confirmation email outside the transaction, with the comment "verification is optional".

So there is no "check your email to continue" wall, and designing one would invent a barrier the backend does not have. The second frame is the dashboard, with a dismissible nudge.

Login never checks emailVerifiedAt either.

A GUEST MUST NEVER BE SHOWN REGISTER. register() creates a NEW user, so a guest who used it would be signed in as somebody else and every group they made would be stranded on the account they just walked away from.

upgrade() converts the SAME user in place, keeps the userId, and therefore keeps the groups. That is why the guest banner has its own screen and its own words, and why it counts the groups back at you.

This is the email twin of rule D3 from 0004.

GOOGLE IS DRAWN BUT CANNOT BE WIRED YET, for two separate backend reasons.

1. GET /v1/auth/google/callback returns AuthTokens as JSON, so a browser lands on a page of JSON instead of coming back to the app. It needs to 302 back with the pair in the URL fragment.

2. The callback sends the profile with no linkUserId, and linkUserId is the parameter that upgrades a guest in place. Without it a guest who taps Google is handed a brand new registered account and loses their groups, exactly as if they had used register.

So the button stays recorded until both land. Both are backend work the user reserved.

ONE ERROR FOR BOTH CAUSES, on purpose. login() returns the same UnauthorizedException whether the email is unknown or the password is wrong, with the comment that this is so the response does not reveal which emails are registered.

So the screen must never say "no account with that email", and the message hangs under the pair of fields rather than under one of them.

RESENDING IS PLAIN TEXT, NOT A BUTTON (user decision 2026-08-26). One sentence inside the card: amber while it can be used, then it becomes its own reply and counts down for a minute before returning.

It is deliberately quiet. Confirming is optional, so the affordance must not compete with the group actions underneath it.

THE COUNTDOWN IS THE SERVER'S NUMBER, NOT SIXTY. The refused state exists because the verifyResend bucket is 3 per 10 minutes, so the fourth ask waits far longer than a minute. A hardcoded 60 would count to zero and then fail again. The client reads retryAfterSeconds from the response BODY: enableCors sets no exposedHeaders, so a browser cannot read a Retry-After header cross origin.

Both the resend endpoint and sending a verification on upgrade are being implemented by the user.

PLAN 0148, STAGE 0. A forgotten password has a way back. Backend 0210 sends one mail with two links that share one token: a reset link, and a sign in link (the same address plus mode=sign-in). Using either ends both, and ends every older link of that person.

Both links open ONE page, auth/reset-password, in two modes. The second action switches the mode in place and keeps the token.

Night only, as the rest of this folder: no new colour role.

THE RESET LINK SPENDS NOTHING ON LOAD. Mail scanners open links, so the page reads the token, takes it out of the URL, and waits for a button.

THE SIGN IN LINK HAS NO SCREEN (the owner's pick 2). It spends the link as the page loads and lands on home. While the request runs the page shows the spinner the confirmation link page already shows, and nothing else. The owner accepted the risk: a mail scanner that runs scripts can spend the link first, and it then arrives dead. The reset link still waits for a press.

If the owner of the link is already signed in, either way into it lands on home with no error, even when the link is old.

THE FORGOT PAGE NEVER SAYS WHETHER AN ACCOUNT EXISTS, and never says a mail arrived. forgot-password answers the same for every address, so the copy says what we did ("if it has an account, we have sent it a mail"). The wait is the server's number (rule C3), as on the resend line.

The address comes over from the sign in page, so a person who just failed to sign in types nothing again.

THE OWNER'S PICKS, 2026-10-14.

1. The reset link is design C: the OR rule and the outlined Keep my password and sign in, the same pair the sign in page uses for Google.

2. The sign in link shows no screen. Its alternatives are gone from this canvas.

3 and 4. The confirm is a message with one button that continues. For a guest the last paragraph carries a plain link to the upgrade page, which keeps the groups. No second button.

5. Each confirm names the username and the email of the account on this phone, always.

6. No support session screen. The backend still refuses the link inside one, and the page shows that answer as the dead link screen.

THE CONFIRM IS A STATE OF THE PAGE, NOT A SHEET. It has one button, so there is no cancel for a sheet to carry. The back chevron is the way out.

SIGN IN LINK: drawn when the server answers recovery_other_account. Its button sends the link again with switchAccount.

RESET LINK: drawn before the reset whenever an account is signed in, because a reset replaces the session too and nothing can tell yet whose link it is. So its words are conditional, and its button saves.

A GUEST IS NEVER OFFERED REGISTER (rule C2). Its button takes the destructive colour of the delete sheet. The group count comes from what the app already holds; with no groups, that sentence goes.

THE DEAD LINK SCREEN, SIGNED IN. The artboard draws a visitor who is signed out. A person who is signed in cannot open the forgot password page or the sign in page, so for them the screen has one button back to their groups instead of the two.
