# 0069 A start warns when the newest probe is red

> Backend half: plan `0247` of `apps/luna-shopper-backend/plans/` (a probe gates a scheduled
> run), built in the same PR that wrote this plan. The owner decided on 2026-11-06, as the
> answer to question 5 of that plan, that a manual start of a preset is never gated, but that
> the back office warns before a person starts a preset or a run whose chain's newest finished
> probe is not `PASSED`, and that the person can start anyway. In the owner's words: "It needs
> a warning, but a run can be started anyway."
>
> Read first: backend `0219` (the probe, its five statuses, `lastProbe` on the source view, the
> probe routes, section 13 for the back office follow up), backend `0247` sections 2, 3 and 6,
> and admin plan `0067` (the schedule page, its words for `blockedBy` and `lastOutcome`).
>
> Mock: none yet. The owner's rule for admin screens is a mock before the plan is built.
> Section 3 says what is drawn, in the parts the back office already has. **Ask the owner
> before you build whether a mock comes first** (Decisions, question 1).

## Brief for the agent

### Objective

Before a person starts a run that reads a chain's storefront, show a quiet notice on the same
form when the newest finished probe of that chain is not `PASSED`. The notice names the chain,
the status, the age of the probe and its one sentence. The start control stays enabled and
starts the run as today. Follow the "Angular conventions" section of `CLAUDE.md`, and use the
`design-taste-frontend`, `antislop`, `antislop-ui`, `antislop-human` and `antislop-copywriting`
skills.

### Context

- **Where a person starts a run of a chain** (`libs/luna-shopper-admin/feature-harvest/src/lib`):
  - `new-run-page.ts`: the page at the Runs tab's "Start a run", which draws
    `RunRequestForm` (`run-request-form.ts`) and calls `HarvestServiceI.spawnRun` on its
    `submitted` output.
  - `presets-panel.ts`: the presets of a chain beside the runs, whose "Start" button
    (`data-start`, `start(preset)`) calls `HarvestServiceI.startPreset`. The panel also edits a
    preset with `RunRequestForm`, but saving a preset starts nothing, so the editor gets no
    notice.
  - `import-upload-page.ts` starts a `FILE_IMPORT`, which reads no storefront. No notice.
  - `shops-queue-page.ts` only links to the Runs tab (`harvest.shops.map.startRun`). No notice.
- **Which runs read the chain** (backend `0247` section 2, step 3): a `CATALOG_DISCOVERY`
  always, a `STORE_DISCOVERY` when the adapter lists its own stores
  (`adapterCapabilities(adapterKey).listsItsOwnStores` in the contracts, true for `lidl-api`,
  `mercadona-api`, `eljamon-web`, `dia-api`, `deza-web` and `carrefour-web` on 2026-11-06), never a
  `FILE_IMPORT`. The six adapters above are also the six that have a probe. `osm-places` and
  `manual` have none.
- **The data on the wire today** (`libs/luna-shopper-admin/models/src/lib/wire/wire-types.ts`,
  regenerated by backend `0247`):
  - `HarvestSupermarketSourceView.lastProbe?: HarvestSourceProbeSummary | null`, where the
    summary is `{ id, status, startedAt, finishedAt, changed }`. It is the newest probe that is
    not `ABORTED`, and it **can be `RUNNING`**. It carries **no `error` and no `attempt`**. The
    sources list sends it (backend `0219` section 8).
  - `GET /v1/admin/harvest/sources/:supermarketId/probes?limit&cursor` answers
    `HarvestSourceProbePage` of `HarvestSourceProbeView`, newest first: `id`, `sourceId`,
    `supermarketId`, `adapterKey`, `trigger`, `status`, `previousStatus`, `changed`, `attempt`,
    `startedAt`, `finishedAt`, `durationMs`, `requests`, `steps`, `error`. `error` is the one
    sentence that names the step and its first problem, null when the probe passed.
  - The admin data access (`libs/luna-shopper-admin/data-access/src/lib/harvest`) has
    `listSources` and `readSource`, and **no method for the probe routes** yet.
- **The schedule page of admin `0067`** (`schedule-view.ts`) translates
  `harvest.schedules.blocked.<block>` and `harvest.schedules.outcome.<outcome>`. Backend `0247`
  added `HarvestScheduleBlock.PROBE_NOT_PASSED` and
  `HarvestScheduleOutcome.SKIPPED_PROBE_FAILED`. Chips for them are the follow up of backend
  `0219` section 13 and are not this plan. The two i18n strings for `PROBE_NOT_PASSED` and
  `SKIPPED_PROBE_FAILED` belong to this plan (target 6), because they are the words of the same
  warning on the schedule page. The review round of backend `0247` (PR #934) shipped both
  strings in `ui/assets/i18n/en.json` with the words of target 6, so this plan only decides the
  chip of the new block.
- **Strings** live in `libs/luna-shopper-admin/ui/assets/i18n/en.json` (English only), under
  `harvest.*`, as admin `0067` put its strings under `harvest.schedules`.

### Target state

1. **A notice on the new run page.** When the chain and the mode chosen in `RunRequestForm`
   read the chain's storefront and the chain's newest finished probe that is not `ABORTED` is
   not `PASSED`, a notice shows above the form's actions: "{chain}'s last probe, {age} ago,
   was {status}: {sentence}. A run may store little or mark products wrong. You can start it
   anyway." It updates when the chain or the mode changes, and it goes away for a mode that
   reads nothing.
2. **The same notice on a preset's Start.** In the presets panel, a preset whose run reads the
   chain shows the notice in its row, under the name, when the chain's newest finished probe is
   red. The Start button stays as it is.
3. **The start control stays enabled** in both places, whatever the probe says, and starts the
   run with the same request as today. No dialog, no second click, no confirmation.
4. **No notice** for a green probe, for a chain with no finished probe, for a probe that is
   `RUNNING` (the newest finished one behind it decides), for a `FILE_IMPORT`, and for a store
   discovery over OpenStreetMap.
5. **The status word** is the person's word, not the enum: "changed shape" for
   `SHAPE_CHANGED`, "refused" for `BLOCKED`, "unreachable" for `UNREACHABLE`, "a fault on our
   side" for `ERROR`. The age is the existing relative format of the harvest feature. A probe
   with no sentence prints the notice without its last clause.
6. **The schedule page words** for the two new values: `harvest.schedules.blocked.PROBE_NOT_PASSED`
   ("{{chain}}'s last probe did not pass. The next slot runs a probe first and is skipped if it
   fails again.") and `harvest.schedules.outcome.SKIPPED_PROBE_FAILED` ("Skipped, the probe did
   not pass").

### Scope

- In: `feature-harvest/src/lib/run-request-form.ts` or `new-run-page.ts` (see section 2),
  `presets-panel.ts`, a new presentational `probe-notice.ts` beside them, a data access method
  for the probe list in `HarvestServiceI` with both implementations (`harvest-api.ts`,
  `harvest-memory.ts`) and the seed, a mapping into an admin model in
  `libs/luna-shopper-admin/models` (rule D4: map from the wire type, never pass it through),
  `en.json`, and their specs.
- Out: the gateway, the harvester, `openapi.json`, `wire-types.ts` by hand, the schedule page
  chips, the import upload page, the source record page.

### Constraints

- The notice never disables, hides or delays the start, and never asks a question. The owner's
  rule is a warning and a free start.
- One read per chain, not one per preset: the presets panel shows one chain at a time, so it
  reads that chain's probes once and shares the answer with every row.
- The newest finished probe is read past `RUNNING` and `ABORTED` rows. Read
  `GET .../sources/:supermarketId/probes?limit=10` and take the first row that is neither. With
  none in the page, there is no notice.
- No dash as punctuation in any string, comment or spec name.
- Icons come from `libs/shared/ui` (`CLAUDE.md`, "Icons are standalone components"). Reuse an
  existing warning glyph if one exists, else add one there. Never inline an `<svg>`.
- If the notice is drawn as an info button, `ui/src/lib/info/info-copy.spec.ts` holds it to a
  title, at most four points of at most 25 words and one caution. It is a notice, not an info
  panel, so prefer a plain `role="status"` paragraph that the spec does not read.
- No named action is added, so `ui/src/lib/action-question-heading.spec.ts` changes nothing.
  If the owner asks for a question instead of a notice (Decisions, question 2), its heading
  holds no placeholder, as that spec requires.
- The tone is the quiet warning tone the harvest feature already uses for "Will not run" on a
  schedule (admin `0067`, target 2): no tinted container, no alert role, nothing that moves.

### Action boundaries

- Ask the owner whether a mock comes first, and the other questions of Decisions. Proceed
  only after the answers.
- Do not start a run or a probe against a live storefront. On a Luna slot, point the chain's
  `config` base URL at a closed local port to make a red probe, as backend `0247`'s slot check
  does.
- Stop and ask if the probe list route answers a shape other than the one in Context.

## 2. Where it is drawn

`RunRequestForm` is shared by the new run page and the preset editor. The notice belongs to a
start, not to the form, so the builder chooses one of two places and says which in the PR:

- **In `new-run-page.ts`**, above the form, fed by the form's `changed` output (the draft
  carries the chain and the mode). The form stays unaware of probes. This is the recommended
  place.
- **In `RunRequestForm`** behind an input that only the new run page sets. Choose it only if
  the draft does not carry the chain and the mode.

In the presets panel the notice sits in the row of each preset whose mode reads the chain,
under the name and above the actions, one line high on a wide screen.

## 3. What is drawn

No new screen and no new section. One paragraph in the warning tone with the warning glyph of
`libs/shared/ui` before it, in the font size of the form's help text. It names the chain by
its name, never its id. On a 390 px screen it wraps; it never truncates the sentence.

## 4. The models

`models/src/lib/harvest/` gains a `ProbeVerdict` model: `{ id, status, startedAt, error }`,
with `status` an admin enum of its own, mapped from `HarvestSourceProbeView` read as `unknown`
(rule D4). A pure function `redProbe(page): ProbeVerdict | null` answers the first row that is
not `RUNNING` or `ABORTED` when it is not `PASSED`, else null. A pure function
`readsTheChain(mode, adapterKey)` answers the rule of Context, with the adapter list read from
`adapterCapabilities` of the contracts if the admin may import it, else from a constant in the
models with a spec that holds it equal to the contracts.

## Decisions

Chosen in this plan, and open to the owner's correction:

- A notice on the form, not a dialog and not a disabled button (the owner's words).
- The notice in the new run page and in the preset row, not in the preset editor, the import
  page or the source page (section 2).
- The probe list route, read once per chain with a page of 10, rather than a backend change to
  the summary (Context). The summary has no `error`, and it can be `RUNNING`.
- The two schedule page strings ride in this plan because they are the same warning
  (target 6). The chips stay with backend `0219` section 13.

**Owner**: ask, do not choose.

1. **The mock.** The owner's rule is a mock before an admin screen is built. Admin `0067` was
   built without one at the owner's request. Draw a mock first, or build from section 3?
2. **Notice or question.** The owner asked for a warning and a free start. A notice keeps the
   start one click. A question ("Start anyway?") makes the person read it. Keep the notice?
3. **The summary.** Should a later backend plan add `error` and `attempt` to
   `HarvestSourceProbeSummary`, so the sources list can show the same sentence without the
   probe route? This plan does not need it.
4. **The source page.** Show the same notice on the source record page beside its probe
   button, or leave that page to backend `0219` section 13?
