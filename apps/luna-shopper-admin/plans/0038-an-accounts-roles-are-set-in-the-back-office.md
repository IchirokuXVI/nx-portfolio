# 0038 An account's roles are set in the back office

> Rewritten on 2026-09-29. The first version was a queue where operators accepted maps that
> shoppers submitted. The shop map series changed: only accounts with the mapping
> permission walk shops, so nothing waits for review, and what the back office needs is a
> way to grant that permission. Nothing of the first version was built.
>
> Back office half of backend `0175` (roles and permissions). Prerequisite reading: backend
> `0175` in full, `libs/luna-shopper-admin/feature-people/src/lib/user-detail-page.ts` (one
> account, with its sections and actions), `users.ts` (the users descriptor), and the
> `admin-app` notes on descriptors.

A velista account now has roles (`admin`, `premium`), and a role grants permissions
(today only `shopMap.record`). Nobody holds a role until an operator grants it, and
the only place to do that is the account's page in the back office.

## Brief for the agent

### Objective

Show an account's roles on its page and in the users list, and let an operator set them
with a confirmation, through `PUT /v1/admin/users/:id/roles`. Use the
`nx-portfolio-angular-developer` skill.

### Context

- **The account page** (`UserDetailPage`) has sections and actions, a confirmation pattern
  (`asking`), and `actionErrorKey` for a refused action.
- **The wire** (backend `0175`): the user rows and the account read carry `roles`, and
  `PUT /v1/admin/users/:id/roles { roles }` sets them. A guest is refused with
  `GUEST_HAS_NO_ROLES`. The account's new permissions reach velista at its next token
  refresh, at most 15 minutes later.
- **Wire types** come from `wire-types.ts`, regenerated by backend `0175`.

### Target state

1. **The account page** has a Roles section: each role with a switch and one line on what
   it grants ("Admin: can map shops." and "Premium: nothing yet."). Changing a switch asks for confirmation, then
   sends the whole set. A guest shows the section disabled with why.
2. **The users list** shows the roles as a column in the table and a line on the card, and
   filters by role.
3. **After a change**, the page says that the account sees it within 15 minutes.
4. **Twins and specs**: the in memory gateway holds one admin account. Screen specs cover
   granting, removing, the guest refusal and the filter.

### Scope

Work only in `libs/luna-shopper-admin/feature-people`, `data-access` and its twins,
`ui/assets/i18n/en.json`, and the specs.

Do not touch: the backend, velista, the operators' own accounts (`admin_users`).

### Constraints

- A role is only ever changed with a confirmation. Nothing changes from the list row.
- `no-literal-resource-path.spec.ts` still passes.
- Only make changes directly requested.

### Action boundaries

Stop and ask before: a bulk role change, a role or permission not in backend `0175`, or
any change to operators.

### Progress evidence

Per target: the files changed and the spec run. At the end: `npx nx test` and `npx nx lint`
for the touched libraries, `npx nx build luna-shopper-admin`, and over HTTP against a slot
serving backend `0175`: grant `admin` to an account, sign in to velista as it, and see the
Walks button on a shop's map after a refresh.
