Overview

Velista is a shared shopping list app. People join a group, keep their lists together and go shopping from one basket that gathers what every list asked for.

It is in production with real users, and it is still in early development, so it keeps changing as I learn what those users need.

It runs on its own domain and installs on a phone like a native app. The same build is also mounted inside this portfolio.

Stack

The frontend is Angular 21, standalone and zoneless, and installable as a PWA. The same app runs on its own origin and as a micro-frontend inside this site.

The backend is seven NestJS services: a gateway, a realtime service, auth, core, catalog, a harvester and an assistant. They talk over NATS, keep their data in four PostgreSQL databases through TypeORM, and share Redis. Live updates reach the browser over Socket.IO.

An assistant built on Gemini adds lines from a sentence or a voice recording, and a separate back office manages the catalog. Everything ships as Docker images to staging and production Kubernetes clusters through Helm and GitHub Actions, tested with Jest and with Playwright suites that shop against a real backend.

How it grew

Velista started as a shared list for a group, built as one more app inside this portfolio.

Live updates and presence came next, so everyone in a group sees the same list at the same moment. Then it moved to its own domain and became installable.

After that came the assistant, and the shared basket: one trip that gathers lines from several lists, open to guests without an account.

The latest stage is prices: a catalog of real products, the shops near a postal code, and a harvester that keeps both current.

The hardest partA catalog you can trust

The hardest part is keeping the catalog valid, and above all its prices. The same product arrives from several supermarket chains under different names and formats, and every name exists in two languages. Deciding what is one product and what is two takes written rules, and a wrong merge shows up at the till.

Every price a source gives is stored side by side, and nothing overwrites it. A policy decides on each read which one a shopper sees, with prices scoped to a shop, a region or a whole chain, and an expired price falls through to the next one.

Records do not enter the catalog on their own. I created a set of libraries to handle their acceptance: a model reviews each waiting record against the naming and merge rules, and the decisions are applied as one file that lands whole or not at all, so a stale or contradictory file writes nothing.

The harvester

Every supermarket publishes differently. One answers with a JSON API, one renders pages that print no price, one publishes weekly offers that differ across dozens of regions, and one only answers a real browser.

Printed leaflets are a source too. A model reads the pages, and each offer waits until it is matched to a product before any price is written. A fuzzy match never writes a price by itself.

Each chain has its own switch in the database, so a source is turned on or off without a deploy.

Baskets and lists

A basket gathers lines from several lists for one trip. A line can be asked for by more than one list, split by the product actually bought, renamed into another line, and settled only when the trip finishes.

All of it updates live for everyone shopping together, including guests without an account.
