# 0004: The license

> The repository is public and has no license. `package.json` says `"license": "MIT"` and
> `"private": true`, `gh repo view` reports `licenseInfo: null`, and no `LICENSE` file
> exists at the root. Without a license file the code is visible but nobody has a clear
> grant to use it, which is the opposite of what the owner decided on 2026-11-02: Velista
> is a product anyone can deploy, the way WordPress is software and wordpress.com is one
> site.
>
> This plan adds the `LICENSE` file at the root of `nx-portfolio`, makes every place that
> states a license agree with it, writes `THIRD_PARTY_NOTICES.md` for the data and code
> in the tree that come from others, and adds a check that keeps the file in place. It
> lands before docs `0005` copies the tree, so the first commit of the new repository can
> be the license alone (owner decision 7).
>
> The choice of license is the owner's. The plan recommends one and explains the
> trade-off for a server product that third parties deploy and that the owner also runs
> as a hosted service.
>
> Paths are written as they are before docs `0003`. After the rename,
> `libs/luna-shopper` is `libs/velista-server`, `libs/velista` is `libs/velista-client`,

> docs `0003` (`apps/luna-shopper-backend/plans` to `apps/velista-server/plans`); this

## Brief for the agent

### Objective

Add the license the owner chose as `LICENSE` at the root of the checkout, in the exact
text GitHub recognises. Make `package.json`, `README.md`, `CONTRIBUTING.md` and the source
comments agree with it. Write `THIRD_PARTY_NOTICES.md` from a checklist that you complete
by reading each source. Add a test, run on every pull request, that fails when `LICENSE`
or the notices file is missing or when `package.json` names a different license. Make
sure nothing in the legal templates of velista promises a license.

### Scope

In: `LICENSE` (new), `THIRD_PARTY_NOTICES.md` (new), `NOTICE` (new, Apache-2.0 only),
the seven `LICENSE` files of target state 3 (only if chosen), `package.json`,
`README.md`, `CONTRIBUTING.md`, the seven `__fixtures__/README.md` files,
`tools/release/license.test.mjs` (new), `.github/workflows/pr.yml` (one step line), and
`legal-settings.ts` or the legal JSON files only if target state 8 finds a sentence that
promises a license.

Out, and why:

- **SPDX headers in source files.** The repository has thousands of files. A root
  `LICENSE` plus the `license` field of `package.json` is what GitHub's license detection
  and the SPDX tooling read, and a header in each file is one more thing to keep equal
  for no reader. The exception is a file that comes from elsewhere and already carries
  its header (the Gradle wrapper): it keeps it.
- **Reducing or deleting fixtures.** Captures are refreshed by each library's
  `capture-fixtures` target and never by hand. Reducing them means changing those
  targets, which is its own work (owner decision 5).
- **A source link in the client.** If the license is AGPL, a modified deployment must
  offer its users the source. A setting for that link belongs with the operator facts
  (backend `0242`) and the client (velista `0178`). This plan records it in the notices
  and as owner decision 6.
- **The license of the new repository.** Docs `0005` copies this `LICENSE` as its first
  commit and checks it with `gh api`.
- **Legal advice.** The checklist states facts the builder can read. Where a question
  needs a lawyer (the database right in captured responses, for example), the notices
  file says so under "Open" and the owner decides.

### Constraints

- Take the license text from a published source, byte for byte. GitHub matches the text
  against its templates, and an edited body makes `licenseInfo` stay null.
- Do not invent the holder's name or the year. Use owner decision 2.
- Every notice entry is backed by a file or a URL the builder read. No entry says
  "probably".
- The test is plain Node with no dependency, like `units.test.mjs`.
- Do not change a legal text's meaning. If target state 8 requires an edit, stop and ask,
  because a change of meaning bumps `LEGAL_TEMPLATES` and asks every account to accept
  again (backend `0231`).

### Action boundaries

- Stop before writing `LICENSE` if owner decisions 1 and 2 are not answered.
- Stop and ask before deleting, reducing or moving any fixture or dataset.
- Stop and ask before any change to the legal JSON files or to `LEGAL_TEMPLATES`.
- Downloading the license text is the only network access. Do not fetch anything else.
- Do not change a GitHub setting.

## Decisions taken in this plan

- **D1. One `LICENSE` at the root, no headers in files.** What GitHub and the SPDX tools
  read, and what a person looks for. Rejected: SPDX headers in every source file.
- **D2. `"private": true` stays.** It stops an accidental `npm publish` of the workspace
  root. It says nothing about the license. Rejected: removing it to look "open".
- **D3. `THIRD_PARTY_NOTICES.md` whatever the license.** The attribution duties of
  GeoNames, OpenStreetMap and the fonts exist under any choice. A `NOTICE` file is added
  only for Apache-2.0, which defines it.
- **D4. The terms never name the license.** The legal texts keep "published under its own
  licence". A license named in the terms would tie a license change to a terms version,
  and every account would be asked to accept again for a change that does not concern
  them.
- **D5. The check lives in `tools/release/license.test.mjs` and runs in the existing
  `pr.yml` step.** That step already runs plain Node tests of repository level rules on
  every pull request, and `tools/release` travels to the new repository with docs `0005`.
  Rejected: adding the assertion to `tools/deploy/units.test.mjs`, whose subject is the
  deploy units, and an Nx project for one assertion.
- **D6. Fixtures stay and get a notice.** The parsers are tested against what the shops
  really serve, and replacing captures with invented markup would test our guess. The
  notice says what they are and that the project license does not cover them. Whether a
  public repository may hold them at all is under "Open" for the owner.

## Owner decisions

1. **The license.** Recommendation: **AGPL-3.0-only**.
   - **MIT** (what `package.json` states today). Anyone may use, change and host Velista,
     and a hosted fork owes nobody its changes. Maximal adoption and the simplest terms.
     A competitor can run an improved copy of the owner's service and keep the
     improvements.
   - **Apache-2.0.** MIT's freedoms plus an explicit patent grant and a `NOTICE` file
     that forks must carry. The same answer as MIT on hosted forks.
   - **AGPL-3.0.** A deployment that runs a modified copy must offer its users the source
     of that copy. Self hosting stays free, and improvements made by a hosted fork come
     back. The WordPress family is GPLv2, which does not reach hosted use; Mastodon,
     Nextcloud and Plausible chose AGPL for exactly the shape Velista has: software
     anyone deploys, and one public instance run by its author. The cost is that some
     companies avoid AGPL code, and that third party clients that import code from the
     repository take on its terms (see decision 3).
   - Why AGPL: the owner's stated model is the WordPress model with the hosted case
     closed. Since the owner holds all the copyright, the owner's own service is not
     bound by the AGPL obligations, and the owner can relax the license later. Tightening
     it later is not possible for code already published under MIT.
   - `-only` versus `-or-later`: `-only` fixes the text the owner read. `-or-later` lets
     a future FSF version apply. Recommendation: `-only`.
2. **The holder and the year.** The name to print in the copyright line, the notices
   header and the README (a person's name, a pseudonym such as the GitHub login, or a
   company), and the first year (the plan does not assume one).
3. **An exception for the shared core.** Docs `0003` tags `contracts`, `basket-rules`,
   `shop-map/model`, `shop-map/recorder`, `shop-map/editor`, `postal-codes` and
   `osm-places` with `scope:shared-core` (its D6), as code any client may use, and backend `0243` builds a second client from
   the contracts. Under AGPL, a closed third party client that imports them must comply
   with AGPL. Recommendation, if decision 1 is AGPL: put those seven libraries under MIT
   with a `LICENSE` in each directory, decided now, while the owner is the only author.
   After outside contributions arrive, the same exception needs every contributor's
   consent. If decision 1 is MIT or Apache-2.0, no exception is needed.
4. **The license of contributions.** Recommendation: one sentence in `CONTRIBUTING.md`,
   "Contributions are accepted under the project license, the license of the files they
   change", and no CLA or DCO sign off. A CLA lets the owner relicense contributions later
   but deters contributors. A DCO adds a sign off to every commit for a project that has
   none yet. The cost of no CLA: every relicensing after the first outside contribution
   needs that contributor's consent, which is why decisions 1 and 3 matter now.
5. **The fixtures.** Recommendation: keep them with the notice of target state 7, and
   open a backlog plan to reduce each capture through its `capture-fixtures` target to
   the elements the parser reads, if the owner wants a smaller footprint. Alternative:
   reduce them before docs `0005` makes the repository public under the new name.
6. **A source link (AGPL only).** Recommendation: add an operator setting for the source
   URL, defaulting to the Velista repository, shown on the client's legal page; built in
   backend `0242` and velista `0178`, not here.
7. **The name and the mark.** Recommendation: state in `README.md` that the license
   covers the code and not the name "Velista" or the brand files under
   `libs/velista-client/ui/assets/brand`, so a fork deploys under its own name. Whether
   to register the name is outside this plan.
8. **The license of `nx-portfolio` itself.** The root `LICENSE` covers the whole
   `nx-portfolio` tree, the portfolio included, until docs `0005` splits it. As the only
   author, the owner can relicense the portfolio's own code later. Recommendation: one
   file for both now; docs `0005` decides whether the archive keeps it.
